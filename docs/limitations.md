# 当前限制

这是黑客松基础版的演示实现：虚构公司、虚构账号、本机服务。下面是已知的边界，按领域列出。

## 尚未验证的部分

- **真实 Agent 模式下的界面全流程**：Rinx 界面实跑（剧本 1–11）是在录制回放与规则模式下做的；真实 octos 只做过各 Agent 步骤的冒烟与命令行对账，没有在 Rinx 里完整走一遍。
- **财务视角的界面**：剧本 12–14 由服务层测试、真实 Matrix 实跑（`matrix_live`）与端到端脚本覆盖，周敏的 Rinx 实例上还没有截图验收。
- **剧本 17 的手动演示**与对账台新增的「简称确认」「漏票跟进」卡片在 Rinx 内嵌页里的样子，待界面核对。
- **方案 B（原生 Octoscript 小程序）** 只做了资料准备，没有实测。
- **Rinx 里 mini_app 卡片的作者显示为「Username not available」**（普通消息作者正常），属 Rinx 行为，未改。

## 适用范围

- 不能用于真实报销：只在本机 loopback 运行，测试房间不加密，政策与历史台账是虚构样例。
- 单一公司、单一币种（人民币），一票对一笔支付；基础版不做拆单与合并支付。
- 申请人名单来自 bot 配置（`applicants`），财务名单来自政策 `finance`。账本里的申请人姓名按演示账号映射（林一、周敏），其他账号取 MXID 本地部分。
- 新批次的期间默认取时钟所在的业务月份（Asia/Shanghai），漏票认领在下个月发生时归入下一期间的批次。配置 `period` 可把所有批次固定到同一期间：`scripts/dev.py` 与真实 Matrix 测试这样做，以便在任何日期用 10 月的演示材料；固定期间下认领的票也记在同一期间。

## 读票与证据

- 原票已付款的重开票（`HISTORY_ALREADY_PAID`）不能再报销：对账台只提供「不报销（移出本批）」，只更换凭证的请线下交给财务。

- 文字层读票只认「标签：值」逐行排列的版式（演示样例即此版式），不是通用电子发票识别器；读不到必填字段、出现第二个无角色的 20 位数字、大小写金额不一致时一律转人工，不猜。
- 图片票由模型读出**候选**事实，须申请人对照原图逐项确认或改正后才入账；改正后的读数再过一次格式校验。模型可能读错甚至编造（真实冒烟中出现过：没拿到图片时编出「Example Merchant」和当天日期），这类读数停在候选级别，不进入关联与入账。
- 微信账单只接受真实导出的 xlsx（表头按内容定位），不接受 CSV；滴滴行程单只接受有文字层的 PDF。
- 商户匹配是启发式：账单商户的前两个汉字（或首个英文词）出现在销售方或备注里，或政策简称表里的简称出现在账单商户中，才算同一商户。匹配不上只会成为「巧合」转人工，不会被自动采用。
- 单文件解析有 20 秒墙钟上限，不直接限制内存；内存由文件大小、解压流、页数、像素与工作簿解包上限间接约束。

## Agent

- 模型只做四件事：图片票读数（A1，候选）、多候选排序（A2，核心复核是否在候选内、是否被占用）、分类与简称建议（A3，类别须在政策枚举内）、说明文字（A4，逐字校验不得编造数字、日期或状态）。不合规重试一次，仍不合规转规则模式并在报告标明。
- 录制回放（`fixtures/agent-replay/demo`）只对演示样例的请求有效；请求不同即取不到录音，该步退回规则。
- 新简称（不在公司简称表里的）在「确认生成」时由申请人确认或修改；公司简称表里的简称固定。

## 授权与会话

- 对账台是本机 HTTP 页面，会话 cookie 不设 Secure（HTTPS 部署时必须设）。配对码 6 位、10 分钟有效、一次性；每个活码最多承受 5 次错误尝试（错码无法归属到某个页面，所以每次错码让所有活码各耗一次），同一发送者 10 分钟内错 5 次锁定；每批次同时最多 20 个未配对会话。
- 这两条防猜码的限制带来两种低成本的拒绝服务，演示环境有意取「防暴力猜码优先」：① 任何能给 bot 发消息的账号（例如无权账号）连发 5 个错码，会作废**所有人**当前的配对码，页面下次刷新换新码、需要重发；② 知道批次 id 的人（卡片链接可以转发）一小时内打开 20 次页面，会用完该批次的未配对会话额度，申请人本人再打开时得到 429。后续改法：按发送者或房间给错码计数分桶、只作废被命中的码；按浏览器会话限制建会话速率，429 时提示稍后重开。
- 配对 1 小时有效，过期后页面重新给码。
- 权限按 `(配对身份, 批次)` 在每次读、下载、变更时校验；财务只读并审批、退回，不能替申请人判断或确认。

## 财务往返

- 退回只解冻被退回条目的业务字段；重新确认时逐字段核对其余条目未变。补充说明按规则模板（事由 + 人数）生成，有长度上限。
- 退回后不能「重开收件」（重新读票会作废全部判断、而其余条目仍冻结）；要改其他内容需联系财务。被退回的条目也可以直接拒收：重新提交时，上一次提交里有、这次没有的票在台账上记为撤回，不再算作已提交，以后仍可正常报销；它的支付会成为漏票候选。
- 历史台账只追加事件（提交、通过；付款与作废事件由核心支持，但对账台未提供财务标记付款的入口）。

## 漏票跟进

- 财务通过时才开始跟进；截止日按政策 `next_month_end`。
- 「以后都不提醒这个商户」按申请人存在编排器里，下次读票生效，不改政策文件（改政策会改变政策哈希、使进行中的快照失效）。
- 「先找」只查报销历史台账，不查其他未提交批次里的票。
- 认领的日期规则：住宿票的支付日须在入住前一天到离店后一天之间；其他票面有服务日期时与支付日相差不超过 1 天，没有时开票日须在支付日与截止日之间。
- 认领的票进入当前开着的批次，但原支付证据不随票带过去：新批次对账时要靠重新上传的账单关联，或由申请人补人工证据。
- 每周提醒只发最近一个到期槽；停机跨过多个周一，恢复后只补发一次（有意避免刷屏）。过截止日只提示一次。

## 运行与恢复

- bot 同步把每个房间的时间线窗口设为 250 条；一次同步里超过这个数的消息仍会被截断，基础版不回补。单批最多 100 个文件。
- 重启后从保存的同步令牌续跑，停机期间的消息会被处理；首次启动（没有令牌）不回放旧历史。
- 产物目标不可写时进入执行等待，约每 30 秒重试一次，不覆盖已发布内容；终审不过三次转人工。
- 端到端脚本用 `clock_file` 驱动时钟；正常运行不设该项，使用系统时间。

## 界面

- 对账台在 Rinx 的原生 mini_app 容器（WKWebView）里打开。开发时用的 Makepad 遥控接口进不了网页叠层：界面实跑里上传文件与网页内点击由 Matrix API 与同一 HTTP 接口代替（见任务报告），真人操作走同一路径。
- mini_app 卡片的作者在 Rinx 里显示「Username not available」（Rinx 行为，普通消息正常）。
- 固定的 Rinx 基线可执行名为 `robrix`，隔离变量为 `ROBRIX_DATA_DIR`。

## 公开仓库

- `scripts/check_public.py` 扫描已知测试凭据、私钥标记、税号、手机号、邮箱与票号模式；PDF 与 XLSX 按文字层与单元格扫描，图片不扫描（仓库里的图片都是代码渲染的虚构样例）。它不等于完整隐私审计。
