# 冻结设计勘误

`docs/design.md`（v1.0）冻结不改；经外环裁定的勘误记在这里，按编号引用。

## A1 · 日限额执行与示例政策额度（2026-09-27，外环裁定，出自 P1 review）

**问题**：示例政策的餐饮日限（150 元）与市内打车日限（50 元）和 §10.1 期望冲突：F05（52.00，单日打车）标「自动」，F09（386.00，单日餐饮）只标「核对视觉读数」。

**裁定**：

1. 日限额照政策执行，从 P2 起：按申请人、服务日期、类别合计后与限额比较；超标项进入待判断，由申请人说明、财务审核。住宿仍按「晚数 × 每晚标准」比较。
2. 示例政策 `local_taxi_per_day_cents` 改为 10000（100 元/天），`meal_per_day_cents` 保持 15000。F05 不再超标。F09 超餐饮日限，但它本来就因视觉读数待判断，只多一条理由：报告计数仍是 6/4/2，入账 10 张、合计 4,901.40 不变。
3. 边界集增加「同一天两笔打车合计超过 100 元 → 待判断」（`fixtures/edge/link/` 的 R07、R08：60 + 55 = 115 元）。
4. `fixtures/expected/link.json` 相应记录 F09 的超标理由。

**实现口径**（P2）：日限额按发票事实所示类别（餐饮、市内客运）与服务日期合计，不按类别标签；只对可信事实计算。F09 在第一遍仍是视觉 candidate，不参与日限合计，理由只有 `FACT_UNCONFIRMED`；用户确认票面后重新关联，才出现 `OVER_LIMIT`，申请人补充说明后记为 `OVER_LIMIT_EXPLAINED`，交财务审核。

## A2 · 终审由六项变为七组（2026-09-27，外环裁定，出自 P1 对抗审查）

**问题**：P1 对抗审查（A3、A4）指出终审只复算了「表 ↔ 快照」，没有复算「快照 ↔ 原件」和「显示 ↔ 值」。

**裁定**：

1. 终审在 §5.6 的六项之外增加第七组 `source_facts`：文字层原件用终审自己的解析重读票号、小写金额、购买方、入住离店；图片票复核确认绑定；按政策复核抬头、类别与发票事实、住宿超标、重开票约束。另外按快照独立重建期望工作簿，与磁盘文件逐字节比对。
2. 设计 DoD 与剧本中的「六项终审 6/6」一律读作「全部检查组全绿」。
3. 面向用户的回帖文案写「终审全部通过（7/7）」。
4. 政策类别新增必填字段 `kind`（lodging / meal / local_taxi / air / other），规则按发票事实触发，类别须与事实一致。

## A3 · 确认快照的内容范围（2026-09-27，出自 P3 对抗审查 A10；外环裁定「补字段或记勘误」二选一，本条取后者，待外环复验）

**问题**：§8.2 把确认快照写成 `{文件哈希清单, 事实（含级别）, 关联, 决定, 政策哈希, 历史台账哈希, revision}`。P3 实现的快照只收入账条目：每张入账发票的全部事实（含级别）、该条目关联得出的服务日期与类别、绑定到这些条目的决定、政策哈希、历史台账哈希、revision。没有单列的文件哈希清单，没有证据事实（账单、行程单、截图），也没有未入账条目的关联。

**处理**：采用缩小后的范围，记为勘误，不改核心的快照模型（快照哈希是执行键，模型由核心 `Snapshot` 严格校验，P1 起冻结）。

1. **快照 = 执行的全部输入。** 打包与终审只读快照与内容寻址对象；快照里有的，执行都用到；执行用到的，都在快照里。
2. **文件哈希**：每个发票事实带 `source.file_sha256`，入账附件的哈希因此都在快照里；终审第七组重读原件并与这些事实比对（勘误 A2）。未入账的文件不影响产物，不收入快照。
3. **证据与关联**：证据只用于在确认前得出服务日期与类别，决定用户看到的报告；确认后执行不再读证据。快照收关联的结论（服务日期、类别）与用户决定，不收证据原文。
4. **P4a「其余不变」的依据**：按稳定 item id 比较快照中该条目的发票事实、服务日期、类别与决定的规范化 JSON，以及附件哈希（`source.file_sha256`）。这些字段都在快照里，比较不依赖证据。
5. 以后若执行开始读取证据，证据事实必须同时进入快照，并改本勘误。

## A4 · 漏票跟进的核心契约细化（2026-09-27，出自 P4c 实现；待外环复验）

**问题**：冻结 spec 把 `claim` 的输入写为 `missing_spends、invoice、evidence、history_snapshot、decisions`，结果为 `match|needs_decision|rejected、reason、next_batch_item`；设计 §5.5 第 3 步的「以后都不提醒这个商户」写入「政策忽略表」；§8.3 的「先找（本批与历史里已有票）」没有指定由哪条命令完成。

**处理**：

1. `claim` 输入为 `missing_spends`、`history_snapshot`，外加二选一：`invoice`（认领：票到了，核验匹配）或 `missing_id`（「先找」：在历史台账里找同商户同金额的票）。漏票行本身带支付事实（商户、金额、支付日期、截止日），不需要 `evidence`；认领不依赖用户决定，不需要 `decisions`。认领结果为 `match|needs_decision|rejected` + `reason` + `missing_id` + `next_batch_item`；「先找」结果为 `found|not_found` + `invoice_nos`。
2. 认领的判定（按顺序）：商户规则匹配（与关联同一规则）→ 事实须可信 → 金额相等 → 日期相符（票面有服务日期时与支付日相差不超过 1 天；否则开票日在支付日与截止日之间）→ 唯一 → 抬头等于政策公司 → 票号不在历史中。商户对上但后续不合格时返回该漏票的 id 和原因，编排器据此回复并留在「等票」（§8.3「不合格回取票办法」）。
3. 「以后都不提醒这个商户」**不改政策文件**：改政策会改变政策哈希，使其他进行中批次的快照失效。改为按申请人存在编排器里，下次读票时作为 `missing` 的可选输入 `ignored_merchants` 传给核心，与政策忽略表合并；报告照旧披露「已忽略商户：…」，对账台可撤销。
4. `missing` 结果增加 `follow_up`：政策里的开票抬头（名称、税号）、提醒规则与截止日。编排器不解析政策文件，跟进所需的政策值都经核心读出。
5. 状态：批次在财务通过时进入「已通过」，同一事务里为每个漏票候选建一条跟进记录（设计「已通过 → 跟进漏票」按笔落在记录上，批次本身关闭）。记录状态：discovered → business → waiting → claimed；或 ignored / found / no_invoice / abandoned 结案。
